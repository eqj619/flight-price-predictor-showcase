# 航空券 価格予測 (flight-price-predictor)

出発空港・到着空港・出発日を指定して航空券価格を毎日モニターし、出発日までの価格推移を予測して**購入タイミングをガイド**する Web アプリ。

登録するとモニター専用の URL（`/w/{token}`）が発行される。アカウント登録もログインも不要で、URL を知っていれば別の端末からでも開ける。

Python 単一スタック（FastAPI + SQLite + ビルド工程なしの静的フロントエンド）。
AWS Lightsail 1インスタンスで稼働する。**342 tests**、うちネットワークを叩くものはゼロ。

---

## 何を解いているか

「いつ買えば一番安いか」は、価格予測としては素直でない問題になる。

- **系列が短く、出発日で永久に終わる。** 1本のモニターはせいぜい数十日分しかデータを持たず、出発日を過ぎると二度と観測できない
- **コールドスタートが常態。** 新しい出発日が登録された瞬間、その系列の観測数はゼロになる
- **知りたいのは次の値ではない。** 「残り期間の最小値がいつ・いくらか」であって、明日の価格ではない

このため学習型の時系列予測が機能しにくい。本アプリは**較正付きドメインモデル**を採る — 航空会社のレベニューマネジメントを模した価格曲線を、その便の実測値でスケール較正して出発日まで外挿する。

> Amazon Forecast は 2024-07-29 に新規顧客への提供を終了しており、選択肢に入らない。

## 主な機能

### 近接空港ルール（既定オフ）

**2026-08-14 に既定をオフへ変更した。** 1モニターが最大4ルートに展開され、
ルート枠の消費が利用者数の 2.4倍になっていたため。機能自体は残し、設定タブで
各自が有効にする。**既存のモニターは自分の設定を保つ** — 既定を変えたからと
いって、監視中の区間を黙って止めてはいけない。

入れ替え可能な空港をまとめて監視する。`SAN → HND` なら SAN/LAX × HND/NRT の**4通り**を追う。

| グループ | 空港 | 向き |
|---|---|---|
| 東京 | HND ⇄ NRT | 双方向 |
| 南カリフォルニア | SAN → LAX | 片方向（LAX 行きの人に SAN は勧めない） |

**近接空港どうしを結ぶ区間（LAX-SAN、HND-NRT）の航空券は収集しない** — そこは陸路などで移動する前提。モニターごとに設定画面で on/off できる。

実測での効果（東京 → 南カリフォルニア、同一出発日）:

| ルート | 最安 |
|---|---|
| HND → SAN | $1,052 |
| **NRT → LAX** | **$473** |

片側ずつではなく組み合わせで展開しているのは、片側ずつだと `LAX ⇄ NRT` が候補から漏れるため。実測で最安だった LCC はまさにその路線を飛んでいた。

### LCC の運賃取りこぼし対策

航空会社を指定しない検索では ZIPAIR の運賃バケットが Google Flights から返ってこない。航空会社を明示指定した追加クエリを発行して拾う。

| 検索 | 最安 |
|---|---|
| 航空会社 無指定 | ANA $2,172 |
| `airlines=["ZG"]` 明示 | **ZIPAIR $494** |

検索ごとに独立して上位N件を取る。全部まとめてから切ると、取りこぼしを拾うための検索結果が通常検索の安値に押し出されて消える。

### 一覧（collections）

モニターの索引は localStorage にしか無かったため、**「サイトデータを削除」で
複数のモニターをまとめて見失う経路があった**。Cookie も IndexedDB も同じ操作で
消えるので、端末の外に置く以外に手段がない。

一覧に専用のトークンを発行し、`/l/{token}` 1本をブックマークすれば全部戻る。
モニターを作ると自動で入る。**モニターと同じ capability**（URL を知っている
＝開ける）として扱う。扱うのが価格と日付だけで個人情報と結びつかないため、
利便性を優先した判断。

| 性質 | 実装 |
|---|---|
| 一覧が中身より先に消えない | 期限を所属モニターの最長期限に追随させる。先に切れると索引を失うという、作った理由そのものが起きる |
| モニターを消したら一覧からも外れる | `ON DELETE CASCADE` |
| 一覧から外してもモニターは残る | `collection_watches` の行だけ消す |
| ログにトークンを残さない | `/l/*` と `/api/collections*` を Caddy の `log_skip` とアプリ側の伏字に追加 |

**1つのパスにトークンが2つ載る**形（`/api/collections/{一覧}/watches/{モニター}`）が
あるため、伏字の正規表現は接頭辞を前方まで含めずに書いてある。

### 空港コードの検証と入力補完

形式（3文字の英字）しか見ていなかったため、`NAR`（NRT の打ち間違い）・
`MIL`（ミラノの**都市**コードで空港ではない）・`CST`（該当なし）がそのまま
収集対象になり、出発日まで毎日失敗し続けていた。利用者には理由の分からない
「取れないモニター」が残るだけだった。

空港マスタ（`static/airports.json`、4,163空港）を**補完と検証の両方から参照**する。
別々のリストを見ていると、画面で選べるのにサーバが拒否する食い違いが必ず起きる。

| | |
|---|---|
| 出典 | [OurAirports](https://ourairports.com/data/)（**パブリックドメイン**） |
| 絞り込み | IATA コードあり かつ 定期便あり |
| 生成 | `python scripts/build_airports.py`（開発時のみ。生成物はコミットする） |

**補完は保証ではない。** 候補を無視して直接入力も、API を直接叩くこともできる。
拒否はサーバ側で行う。都市コード（`TYO`）は空港ではないので拒否するが、
どの空港を指せばよいか（`HND` / `NRT`）まで伝える。黙って代表空港へ読み替えると、
利用者が頼んでいないルートを監視することになる。

マスタは gzip 後 111KB。**入力欄に触れるまで取りに行かない**。以降の照合は
すべてブラウザ内で行うので、打鍵ごとのリクエストは発生しない。

### 所要時間による除外

**最安が実際には選ばれない便であることがある。** 実測（NRT→SAN / 2026-12-20）:

| 便 | 価格 | 総所要 |
|---|---|---|
| NRT-YYC-SAN | **$799** | **33h10**（乗継 20h35） |
| NRT-DFW-SAN | $1,109 | 17h23 |
| NRT-SAN 直行 | $2,473 | 9h35 |

最安の $799 はカルガリーで一晩待つ便で、これが買い時判定の入力になっていた。
総所要（飛行 + 乗継）が既定 24 時間を超える便は、グラフ・最安値・買い時判定の
すべてから外す。モニターごとに変更・解除できる。

**総所要は到着時刻 − 出発時刻では出せない。** 現地時刻なのでタイムゾーンと
日付変更線をまたぐと逆転する（NRT 18:35 発 → YYC 12:45 着）。乗継は同一空港内
なので引き算が成立し、区間の飛行時間の合計に足して求める。**収集時にしか
計算できない**ので、区間の内訳を持たない過去の行は遡って埋められない
（直行便だけは乗継が無いため確定でき、`init-db` が埋め戻す）。

### 予測の「根拠」を3段階で明示する

実測が無いときに黙って推定値を出すと、利用者にはそれが実測と区別できない。`basis` で必ず言い分ける。

| basis | 条件 | 出せるもの |
|---|---|---|
| `observed` | その出発日の実測がある | 3値判定 + 航空会社名 |
| `transferred` | 同じ路線の**別の出発日**に実測がある | 航空会社名（実際に観測された便のみ、便ごとに較正）。3値判定は出さない |
| `simulated` | その路線の実測が皆無 | 曲線のみ。**航空会社名は出さない** |

`transferred` で社名を出せるのは「その路線で実際に返ってきた便」に限る。曲線の係数表から社名を並べると、その社が飛んでいない路線の運賃を出すことになる。

信頼帯の広さは `observed` < `transferred` < `simulated` の順。確かさの順序がそのまま帯の幅に出る。

### 買い時の3値判定

**「今買う / 待つ / 様子見」+ 信頼帯 + 「実測◯日分」**で示す。確信度のパーセントは出さない。

| 条件 | 判定 |
|---|---|
| 予測の**上限** < 今の価格 | 待つ |
| 予測の**点推定** < 今の価格 ≤ 上限 | 様子見 |
| 予測の**点推定** ≥ 今の価格 | 今買う |

信頼帯が効くのは「待つ」と「様子見」の境目。実測が少なく帯が広いうちは言い切らず、日数が増えて帯が狭まると初めて「待つ」が立つ。

## セットアップ

Python 3.12 以降（3.14 / SQLite 3.53 で開発、3.12 / SQLite 3.45 で本番稼働）。

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env          # 既定値のままでも動く

.venv/bin/python -m app.cli init-db
.venv/bin/python -m uvicorn app.main:app --reload
# http://127.0.0.1:8000/
```

価格の収集は外部（Google Flights）へのアクセスを伴う。初回は手動で:

```bash
.venv/bin/python -m app.cli collect --dry-run   # 発行クエリ数と所要時間の見積り
.venv/bin/python -m app.cli collect --once
```

サーバを常駐させておけば、以後は毎日 03:00（`TIMEZONE` 基準）に自動で収集する。常駐させない運用なら cron / launchd から `run-daily` を叩く。

### コマンド

```
init-db                              スキーマを適用（冪等）
add-route ORIGIN DEST YYYY-MM-DD     モニターを手動登録
routes / status                      監視中ルート・収集状況
collect --dry-run | --once           価格収集
predict [ORIGIN DEST DATE] [--log]   予測と買い時判定
sync-routes [--dry-run]              近接空港ルール変更後にルートを張り替える
run-daily                            日次ジョブ（整理 → 収集 → 予測 → KPI）
kpi [--dry-run|--show]               利用状況を CSV に記録し S3 へ写す
```

```bash
.venv/bin/python -m pytest tests/ -q      # 342 tests。ネットワーク不要
```

### 蓄積データの取り出し

```bash
.venv/bin/python -m app.cli dataset                          # 蓄積状況
.venv/bin/python -m app.cli export --out prices.csv          # 実測を CSV で
.venv/bin/python -m app.cli export --completed-only          # 出発日を迎えた系列だけ
.venv/bin/python -m app.cli export --table predictions       # 予測 vs 実測
```

### 利用状況の記録（KPI）

日次ジョブが収集の後に、その日の KPI を1行 CSV に追記する。**列は英語で固定**。

```bash
.venv/bin/python -m app.cli kpi --dry-run   # 書かずに当日の値を見る
.venv/bin/python -m app.cli kpi             # 記録して S3 へ写す
.venv/bin/python -m app.cli kpi --show      # これまでの記録
```

需要（`watches_total` / `distinct_creators`）、容量（`routes_active` / `routes_utilization_pct`）、
当日の収集（`collection_status` / `records_collected`）、蓄積量（`snapshots_real` / `series_completed`）の23列。

**ローカルの CSV が正で、S3 はその写し。** 毎日まるごと置き換える。逆にすると
アップロードが失敗した日の行が永久に欠ける。S3 が落ちていても収集は止めない
（アップロードの失敗は握りつぶす）。

**列は末尾にしか足さない。** 途中に挿入すると過去に書いた行と列がずれる。

価格のほかに、出発・到着時刻、飛行時間、機材、CO2 排出量、
`days_to_departure` を記録している。**取得時にしか取れない項目は、いま
予測に使っていなくても捨てない**という方針（遡って取得できないため）。

## 構成

```
app/
  api/        FastAPI エンドポイント + 入力検証
  collect/    価格収集（PriceProvider 抽象 + fast_flights 実装）
  predict/    価格曲線・較正・信頼帯・買い時判定
  db/         スキーマとリポジトリ層（SQL はここにしか書かない）
  jobs/       日次ジョブとスケジューラ
static/       ダッシュボード / 価格トレンド / 買い時分析 / 設定 の4タブ
deploy/       systemd unit・Caddyfile・構築と配備のスクリプト
docs/         仕様書・デプロイプラン・構成図
```

日次の API コストは**利用者数ではなく「異なる (出発, 到着, 出発日) の数」に比例する**。同じ条件を何人が登録しても収集は1回で済むよう、利用者視点の `watches` と収集対象の `monitored_routes` を分けてある。

設計上の不変条件と、それを守る理由は [CLAUDE.md](CLAUDE.md) にまとめてある。

### デプロイ

AWS Lightsail 1インスタンス（Caddy で TLS 終端 → uvicorn → SQLite、APScheduler 同居）。
構成図・費用・採用しなかったサービスの理由は [docs/aws-architecture.html](docs/aws-architecture.html)、
監視中の路線マップは [docs/route-map.html](docs/route-map.html)（英語版 [route-map.en.html](docs/route-map.en.html)、
生成は `python scripts/build_route_map.py`）、
手順は [deploy/README.md](deploy/README.md)。

**匿名運用の前提として、次の3つを守っている。**

- トークンは `secrets.token_urlsafe(16)` で発行し、**アクセスログ・エラーログ・外部送信先に平文で残さない**
  （Chart.js を CDN ではなく同梱しているのは、CDN へのリクエストの `Referer` にトークン付き URL が載るため）
- `/w/{token}` は `noindex`。存在しないトークンでも同じ HTML を返す（総当たりに情報を与えない）
- IP は生で保存せず、ソルト付きハッシュのみ。`X-Forwarded-For` は既定で信用しない

## 決定済みの設計方針

| 項目 | 決定 | 理由 |
|---|---|---|
| マルチユーザー方式 | 匿名マルチテナント（URL トークン + localStorage） | 扱うデータに秘匿性がなく、認証のコストに見合わない |
| 予測方式 | 較正付きドメインモデル | 系列が短く出発日で途切れ、コールドスタートが常態のため |
| 価格データソース | `fast_flights`。`PriceProvider` 抽象で差し替え可能 | 非公式スクレイパなので隔離する |
| 原油価格 | EIA Brent + 3ヶ月ラグを実装。**係数は 0（無効）** | 最長60日の監視期間では寄与がほぼ定数になり、較正のスケール項に吸収される |
| 通知 | なし（`notify_email` 列のみ用意） | — |
| 上限 | 全体 **1,000** ルート / IP あたり 10 件・日 / 同時 20 件 | 匿名なので人単位で縛れない。8割で日次ジョブが警告する |
| 通貨・言語 | USD 固定、日本語 / 英語 | — |

## 現状の限界

既知の課題は [docs/issues.md](docs/issues.md) に1件ずつ積んである。以下はそのうち
構造的なもの。


- **買い時判定に非対称性がある。** 「待つ」には信頼帯によるゲートがあるが「今買う」にはない。曲線の日次傾き（直前期でも3〜4%）が帯の最低幅5%を超えられず、下限でゲートすると「今買う」が原理的にほぼ出なくなるため。実測日数のラベルを必ず併記することで補っている
- **価格曲線のパラメータは実測から推定したものではない。** 東京〜米西海岸市場の観測に基づく初期値。完了した系列が貯まったら推定値に差し替える（パラメータは `app/predict/curve.py` に外出し済み、JSON でも上書き可）。
  **繁忙期（感謝祭・年末年始）は予約が早く入り底も早く来ると予想されるが、
  現在のモデルはこれを表現できない** — `proximity_factor` が日数しか受け取らず、
  底は出発日によらず常に 45〜75 日前になる。季節性は水準を上下させるだけで、
  月単位なので感謝祭（11月 = 1.00）は5月と同じ扱い。**較正でも直らない**
  （スケール項なので水準しか動かせない）。観測計画は
  [docs/holiday-observation-plan.md](docs/holiday-observation-plan.md)。
  2026-08-11 時点の断面では、実測の最安が出た日は 28/79/79/79/79/112/118/118 日前で、
  **底値帯とした 45〜75 日前には1件も入っていない**。出発日をまたぐ断面なので季節性と
  交絡し反証にはならないが、支持する証拠にもなっていない。画面の文言もこの状態に
  合わせてある（「目安」「検証中」と明示する）
- **`fast_flights` は非公式の Google Flights スクレイパ。** いつ壊れてもおかしくないため `PriceProvider` 抽象の裏に隔離してある。日次1,500リクエスト規模での挙動は継続監視が必要
- **SQLite 単一インスタンス。** 水平スケールしない。必要になれば Postgres へ移せるよう、SQL は `db/repository.py` に閉じ込めてある

## 由来

2つの先行プロジェクトを調査したうえで作り直したもの。

| 引き継いだもの | 引き継がなかったもの |
|---|---|
| 価格モデルと較正の考え方 | 直近1点だけの較正（外れ値1つで予測全体が歪む） |
| 収集時の実運用知見（該当便なしの判定、セグメント数検証、ポライトネス） | 過去日を「推奨購入日」として返す買い時判定 |
| フロントエンドの i18n パターン、スケジューラの多重起動ガード | 固定の確信度パーセント（95/85/80…） |
| | シミュレーション値しか読まないダッシュボード |

先行実装にあった4つの欠陥（1点較正・過去日の推奨・信頼帯なし・シミュレーション値の混入）は、いずれも構造的に修正したうえで回帰テストで固定してある。

## 注意

- **価格データの取得元の利用条件は各自の責任で確認すること。** 本リポジトリは特定のデータソースの利用を推奨するものではなく、`PriceProvider` 抽象によって公式 API へ差し替えられる設計になっている
- **表示される価格・予測・買い時判定はいかなる保証も伴わない。** 実際の購入判断は各自の責任で行うこと
