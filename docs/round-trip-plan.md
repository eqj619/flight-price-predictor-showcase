# 往復（round-trip）対応の計画

課題5。要望が多いので着手する。**2026-08-19 に実際のクエリを投げて確かめた事実**を
先に置き、そこから設計を決める。推測で組むと、課題2と同じ失敗（未検証のモデルを
判定に使う）を繰り返す。

## 1. 実測で分かったこと

### 1.1 ライブラリは対応している

`create_query(trip="round-trip")` は既にあり、`FlightQuery` を2本渡す。
我々の `fast_flights_provider._search` が `trip="one-way"` を直に書いているだけ。

### 1.2 応答の形が非対称 — **ここが最大の落とし穴**

NRT→LAX 11/10、復路 LAX→NRT 11/20、直行のみで実行した結果:

```
price=1585  airlines=['ZIPAIR Tokyo']       セグメント数=1  NRT->LAX 11/10 14:45
price=2033  airlines=['Singapore Airlines']  セグメント数=1  NRT->LAX 11/10 18:15
price=2226  airlines=['ANA']                 セグメント数=1  NRT->LAX 11/10 17:00
```

**価格は往復の合計。セグメントは往路だけ。復路は応答に入っていない。**

これをそのまま今の `snapshots` に入れると「NRT→LAX 直行 ANA $2,226、所要◯分」という
行になる。金額は往復、所要は往路。**別々の量が1行に同居する。** 気づかないまま
較正と買い時判定に流れ込む。

影響を受けるのは `_flight_details` が埋める全部 —
`departure_time` / `arrival_time` / `air_minutes` / `total_minutes` / `plane_types` /
`carbon_g`。すべて往路のみの値になる。

### 1.3 往復は片道から作れない

同じ日付・同じ区間で片道も引いて比べた。

| 航空会社 | 片道 往路 | 片道 復路 | 往復 |
|---|---|---|---|
| ANA | $2,164 | （返らず） | **$2,226** |
| JAL | $2,195 | （返らず） | $2,317 |
| ZIPAIR | （返らず） | $1,309 | **$1,585** |
| Singapore | （返らず） | $1,760 | $2,033 |

**ANA は往復が片道 +$62。** 2倍ではないどころか、ほぼ片道の値段で往復が買える。
往復価格は片道2本の合成では出せない別の量であり、**別に収集する以外にない。**

（片道と往復で返る航空会社の顔ぶれも違う。在庫の出方が違う。）

### 1.4 価格履歴は往復でも取れる — **これは朗報**

`payload[5][10][0]` の60日分は往復クエリでも返った。

```
62点  2026-06-19 〜 2026-08-19  $875 〜 $1,152
```

つまり**往復の価格曲線は、収集を待たずにいま検証できる。** 片道のときに
212系列/13,004点を遡って取ったのと同じ手が使える。往復モニターも初日から
過去60日を表示できる。

## 2. 一番危ないところ — UNIQUE 制約は ALTER TABLE で変えられない

`return_date` を足すだけでは**足りない**。`snapshots` の UNIQUE は

```
UNIQUE (check_date, departure_date, origin, destination, stops, via_airport, airline)
```

で、`return_date` がここに入らない限り、**同じ区間・同じ日の片道と往復は同一行と
判定される。** 実際に試した:

```
INSERT OR REPLACE 片道   NRT->LAX 11/10 ANA $2,164 (return_date='')
INSERT OR REPLACE 往復   NRT->LAX 11/10 ANA $2,226 (return_date='2026-11-20')
→ 残った行数 = 1   片道が往復に潰された
```

そして SQLite のテーブル定義内 UNIQUE は `sqlite_autoindex_snapshots_1` という
暗黙インデックスになり、**DROP できない。** `_apply_column_migrations` の
`ALTER TABLE ADD COLUMN` 方式ではどうにもならない。

**テーブル再構築（新テーブル作成 → コピー → 差し替え）が要る。**
対象は UNIQUE に `return_date` を含める必要がある4つ:

| テーブル | 現在の UNIQUE | 再構築 |
|---|---|---|
| `monitored_routes` | (origin, destination, departure_date) | **要** |
| `snapshots` | (check_date, departure_date, origin, destination, stops, via_airport, airline) | **要** |
| `prediction_log` | (predicted_on, target_check_date, departure_date, …) | **要** |
| `price_history` | (origin, destination, departure_date, observed_date) | **要** |

`watches` は UNIQUE に日付を含まないので `ALTER TABLE` で足せる。
`fetch_errors` は UNIQUE 無し、同じく足すだけ。

### 決めておくこと

**`return_date TEXT NOT NULL DEFAULT ''`（NULL 許容にしない）。**
schema.sql の `via_airport` に同じ教訓が既に書いてある — SQLite は
`NULL != NULL` なので、NULL 許容にすると片道行の重複排除が黙って壊れる。
`''` = 片道、日付が入っていれば往復。

## 3. 段階

**判定（買い時）を出すのは最後。** 曲線が往復にも当てはまるか測ってからにする。
これは課題2で一度やった失敗の繰り返しを避けるため。

### 段階A — 器（スキーマ）✅ 2026-08-19 完了・配備済み

- `return_date` を4テーブルに追加し、UNIQUE に含める
- テーブル再構築の関数を `connection.py` に足す。冪等・トランザクション内・
  件数照合つき。既存行は `return_date=''`
- **本番 DB のバックアップを取ってから。** 7.2MB、スナップショット11,222点。
  日次ジョブ（03:00 PT）と重ならない時間に実施
- **読み出し側を明示する。** ここが自動では守られない。`repository.py` に区間で
  絞る問い合わせが8箇所あり（807, 877, 941, 1268 ほか）、いまは
  `origin / destination / departure_date` の3つで絞っている。往復の行が同じ
  テーブルに入ると、この条件だけでは**往復も一緒に拾う**。片道の系列に
  往復価格（金額がほぼ2倍）が紛れ込み、較正が静かに狂う。
  **8箇所すべてに `return_date` を明示する。1箇所でも漏れると既存の片道
  モニターの予測が壊れる。**
- テスト: 再構築が既存データを1件も失わないこと、片道と往復が別行として
  共存すること、**片道の問い合わせに往復の行が1件も混ざらないこと**

### 段階B — 収集 ✅ 2026-08-19 完了（未配備）

- `PriceProvider.fetch` に `return_date: Optional[date] = None` を足す
  （既定 None = 片道。既存の呼び出しは無変更で通る）
- `_search` は `return_date` があれば `FlightQuery` を2本にし `trip="round-trip"`
- **`_flight_details` は往路のみの値だと明示する。** 列名は変えず、`Quote` に
  `leg_scope` の概念をコメントで固定し、往復のときは
  `departure_time`/`arrival_time` が往路を指すことを docstring に書く
- `expand_routes` は往復でも同じ（近接空港の組み合わせは変わらない）。
  **1往復モニター = 1クエリ = 1ルート。** 片道と同じ枠しか食わない
- `max_total_minutes` は**往路にしか効かない**。復路の所要は取れない。
  UI の表記も「往路の所要時間」に変える
- 経由回数の検証 `len(fg.flights) - 1 != stops` は往路のみの検証になる。
  復路の経由回数は指定はできても検証できない。コメントに残す

### 段階C — 往復の曲線を測る（**判定を出す前に必ず**）🔄 観測中

- 調査用モニター（`purpose='research'`）を往復で入れ、`backfill-history` で
  60日分を遡る。片道のときと同じ手順
- 測ること:
  1. 出発何日前が安いか。片道の 50〜59日前 / −4.2% と一致するか
  2. **滞在日数が効くか。** 往復には片道に無い次元がある。7泊と14泊で
     曲線が違うなら、`sweet_spot` を滞在日数で変える必要がある
  3. 出発30日前以降の上昇（片道は +16.7%）が往復でも同じか
- 結果を `docs/` に残す。片道のときと同じ形式で、系列を標本単位とした対比較

### 段階D — 予測と判定 ⏸ 段階Cの結果待ち

- `build_trend` / `calibrate` / `recommend` に `return_date` を通す。
  較正は区間ごとの実測から出るので、往復系列は**自分の履歴で自分を較正する**。
  ここは構造的には片道と同じ
- 曲線パラメータは段階Cの結果しだい。**片道と同じでよいと分かるまで、
  往復には判定を出さない**（価格と履歴だけ見せる）

### 段階E — 画面 ✅ 2026-08-19 完了

- 登録フォームに片道/往復の切り替えと復路日の入力。
  復路日 > 出発日 の検証を `WatchCreate` に入れる
- 一覧・詳細に往復の表示。金額が往復合計であることを明示する
  （**ここを曖昧にすると片道と比べて「高い」と誤解される**）
- i18n 日英とも。`changelog.js` に1行（利用者に見える変更）

### 段階F — 配備

- 段階Aだけ先に本番へ入れて1日回す（既存の収集が壊れていないことを確認）
- そのあとB以降

## 4. 容量への影響

いま 331/1000（33%）、収集63分、1ルート11.4秒。

**往復1件は1クエリなので、片道1件と同じコスト。** ただし往復対応で
「片道と往復を両方見たい」利用者が出れば、1人あたりの消費は増える。
669ルートの余裕があるので当面は問題にならないが、1000ルートで約3.2時間になる
（03:00開始）。

## 5. 決めきれていないこと

- **復路の便が分からないまま「往復◯◯円」と出してよいか。** Google Flights 自身が
  往路選択の画面でこう見せているので利用者の期待とは合う。ただし
  「その価格で買える復路がどれか」は我々のデータに無い
- 段階Cで滞在日数が効くと出た場合、曲線の作り直しが要る。その規模はいま読めない
- 往復の `snapshots` が片道の何倍の行を生むか。区間×出発日×**復路日**なので、
  復路日の選択肢が多い利用者が増えると行数が伸びる

### 段階B（2026-08-19 完了、未配備）

実物の provider で通した結果:

```
往復 NRT->LAX 11/10 復路11/20   $1,586 ZIPAIR / $2,231 ANA / $2,322 JAL
片道 NRT->LAX 11/10             $2,168 ANA  / $2,200 JAL
履歴（往復）                     62点 2026-06-19〜2026-08-19
```

**非対称がそのまま見えている。** ANA は往復 $2,231 だが `total_minutes` は
590分（約10時間 = 往路のみ）。価格は往復、所要は往路。

**この1件から「往復は片道とほぼ同額」と読むのは誤り**（2026-08-19 訂正）。
4区間46系列でならすと往復は片道の **1.85倍**（1.21〜2.45）。上は直行便に
絞った1件で、その片道が異常に高かった場合。「片道から往復は作れない」と
いう結論は変わらないが、根拠は「倍率が一定しないから」である。
docs/round-trip-findings-2026-08-19.md §4。

**利用者はまだ往復モニターを作れない。** API のスキーマも画面も片道のまま
（段階E）。この時点で動くのは、往復ルートが `monitored_routes` にあれば
収集される、というところまで。
