# 通知の設計（2026-08-20）

課題4。**買い時が分かっても伝える手段がない**を塞ぐ。

利用者と合意した条件は2つ。**どちらも「送るたびに言うことがある」**を満たす。

## 1. 何を送るか

### ① これまでで一番安い値を更新したとき

```
条件  そのモニターの最安が、観測開始以来の最安を 1% 以上 下回った
頻度  週 0.40 回（実測 214系列で試算）。時間とともに減る
```

**「1円でも下がったら」にしない。** 日次の値動きは中央値 0.13%（ルート最安）で、
更新幅の **54% は 1% 未満**。薄い更新で通知を1回使うと、本当に効く通知まで
価値が下がる。

| 条件 | 週あたり | 最大 | 鳴る系列 |
|---|---|---|---|
| 更新すれば何%でも | 0.88 | 4.4 | 137/214 |
| **1%以上** | **0.40** | 3.5 | **81/214** |
| 2%以上 | 0.35 | 3.5 | 71/214 |
| 3%以上 | 0.31 | 3.5 | 65/214 |

1% から 3% に締めても 0.40 → 0.31 しか減らない。**意味のある更新はもともと
大きい**ので、1% で切れば十分。

**この規則は自然に減衰する。** 観測 n 日目に最安を更新した割合は
2日目 24.0% → 4日目 8.9% → 8日目 8.6% → 11日目 7.9%。走っている最小値が
落ち着くため。「1円でも下がったら」は永久に週1.5回のまま減らない。

### ② 値上がりが始まる前（出発30日前を跨ぐとき）

```
条件  画面が「値上がり開始日」として出している日。1モニターにつき生涯1回
根拠  出発30日前を過ぎると平均 +16.7%（35/41系列, 符号検定 z=+4.5）
```

**当初「出発30日前を切る最初の収集日」と書いたが、実装時に変えた**
（2026-08-21）。画面は `price_rises_after`（出発52日前 = 曲線の
`sweet_spot_start_days`）を「値上がり開始日」として既に出しており、
**別の日に通知が来ると説明できない。** 30日は本文で使う
（「出発30日前を過ぎると平均17%高くなります」）。

30日ちょうどで鳴らすと猶予がゼロになる、という問題も同時に解ける。

**我々が確度をもって言える唯一のこと。** 谷（50〜59日前 −4.2%）はこれの
4分の1しかなく、通知の根拠には弱い。

**作成時点で既に30日以内のモニターには送らない。** 「これから上がる」という
知らせであって、「もう上がっている」ではないため。画面には従来どおり出す。

### 却下した案 — 「1週間閲覧がない」

利用者から出た案だが**採らない。**

- **中身が無い。** 「見に来てください」以外に言うことがない
- **我々の指標のための通知になる。** 定着率を上げたいのは我々の都合で、
  利用者の利益ではない
- **本日のKPIでは 116件中77件が未再訪。週77通、内容ゼロになる**
- **代償が重い。** Web Push の許可は一度断られると出し直せない。中身の無い
  通知で断られると、②を送る手段まで失う

②が「しばらく開いていない人を呼び戻す」という狙いを、中身つきで果たす。

## 2. 送らないもの

**往復には②を送らない。** 遅延の罰（+16.7%）は片道 212系列から出した値で、
往復では未測定（docs/round-trip-findings-2026-08-19.md §5）。画面で判定を
出していないのと同じ理由。**①は往復にも送れる** — 実測の最安更新なので
曲線に依存しない。

測れる見込みは 2026-10 中旬。それまで往復は①のみ。

## 3. Web Push の構成

```
① 購読                     ② 送信                   ③ 受信
ブラウザ                   日次ジョブ                ブラウザ（閉じていてよい）
  subscribe(VAPID公開鍵)     条件を判定                Service Worker が起きる
  → endpoint/p256dh/auth     本文を暗号化(RFC 8291)    showNotification()
  → サーバに保存             VAPID署名(RFC 8292)
                             endpoint に POST
                                  ↓
                        プッシュサービス（Google/Mozilla/Apple）
```

**メールアドレスを持たずに済む。** ここが SES 案との決定的な違い。

## 4. データ構造

`collections` / `collection_watches` と同じ形にする（既にある作法に合わせる）。

```sql
CREATE TABLE push_subscriptions (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    endpoint   TEXT NOT NULL UNIQUE,     -- プッシュサービスのURL
    p256dh     TEXT NOT NULL,            -- 暗号化用の公開鍵
    auth       TEXT NOT NULL,            -- 認証用の秘密値
    created_at TEXT NOT NULL,
    last_seen_at TEXT NOT NULL,          -- 画面を開くたびに更新
    last_sent_at TEXT                    -- 1日1通の上限に使う
);

CREATE TABLE push_subscription_watches (
    subscription_id INTEGER NOT NULL REFERENCES push_subscriptions(id) ON DELETE CASCADE,
    watch_id        INTEGER NOT NULL REFERENCES watches(id)            ON DELETE CASCADE,
    PRIMARY KEY (subscription_id, watch_id)
);
```

送信済みの状態は watches 側に持つ。**同じことを二度送らないため。**

```sql
ALTER TABLE watches ADD COLUMN notified_low_usd REAL;      -- ①で最後に送った最安
ALTER TABLE watches ADD COLUMN notified_rise_at TEXT;      -- ②を送った日
```

## 5. 匿名性への影響 — 設計の前提が変わる

いまは個人情報を一切持たない。それが「一覧のトークンが漏れても個人と
紐づかない」という判断（仕様2.4）の前提になっている。

**endpoint は個人情報ではないが、匿名でもない。** ブラウザごとに固定の
文字列で、その端末を継続的に指せる。**仮名**である。

| | メール（案A） | Web Push（案B） |
|---|---|---|
| 保存するもの | メールアドレス | endpoint URL |
| 個人と紐づくか | **紐づく** | 紐づかない |
| 端末を追えるか | — | **追える** |
| 利用者が切れるか | 配信停止の導線が要る | **ブラウザ設定で即時** |

**この差は画面で説明する。** 「通知を受け取るために、この端末を指す文字列を
保存します。メールアドレスなどは受け取りません。ブラウザの設定でいつでも
切れます」。

## 6. 許可を求めるタイミング

**読み込み時に自動で出さない。** 断られたら二度と出せないため。

モニター詳細に「値上がり前に知らせる」ボタンを置き、**押されたときだけ**
`subscribe()` を呼ぶ。利用者が通知の目的を理解した状態で許可を求める。

## 7. 日次ジョブへの組み込み

収集と予測のあと、新しい段として足す。**既存の段と同じく、失敗しても
ジョブ全体を落とさない**（try/except で握って `failed_steps` に積む）。

1モニターにつき**1日1通まで**。①と②が同じ日に該当したら**②を優先**する
（生涯1回で時期が決まっているため）。

## 8. 失敗と後始末

- `404` / `410` → 購読が死んでいる。**行を消す**
- `429` / `5xx` → 次回に回す。消さない
- 送信は1件ずつ独立に扱い、1件の失敗で残りを止めない

## 9. iOS の制約 — 実機で確認済み（2026-08-21）

iOS Safari は 16.4 以降で Web Push に対応するが、**ホーム画面に追加した
場合だけ**。通常のタブでは受け取れない。**2026年時点でも続いていることを
iPad で確認した**（下記）。

→ `manifest.json` と「ホーム画面に追加」の案内が要る。**それでも iPhone の
利用者の多くは離脱する。**

### 段階Dで入れたもの（2026-08-21）

- `manifest.json`。**`scope` を `/` と明示した。** manifest 自体は
  `/static` 配下にあるので、省くと既定が `/static/` になり、モニター画面
  （`/w/{token}`）が単独窓の外に出る。iOS ではそこが通知の可否に直結する
- `apple-mobile-web-app-capable` ほかの apple- 系タグ。**iOS は manifest の
  `display` を見ない。** 単独窓になるかはこのタグだけで決まる
- iOS を「非対応」で片付けるのをやめ、**共有ボタンからの手順を出す**
  （`push.ios`）。iPad は自分を Mac と名乗るので `maxTouchPoints` も見る
- アイコン一式。**`badge` は色付きアイコンの使い回しにしない** — Android は
  badge をアルファだけ見る白黒のマスクとして扱うので、四角い塊になる

**アイコン欠落は実害が出ていた。** `sw.js` は 8/20 の段階Aから
`/static/icon-192.png` を指していたが画像が無く、鍵を入れた 8/21 以降の
通知はアイコン無しで配信されていた。参照先の実在を見る試験を足した
（`tests/test_frontend.py::test_every_referenced_image_exists`）。

### 実機で確認した（2026-08-21、iPad）

**制約は続いていた。** 利用者の iPad で確かめた結果:

| Chrome のタブ | 購読できない。チェックボックスが反応しない |
|---|---|
| **Safari → ホーム画面に追加 → アイコンから起動** | **購読できた**（`web.push.apple.com` の宛先が登録された） |

したがって §9 の見積りはそのまま有効。**iOS はホーム画面に追加した
アプリでのみ Web Push が動く。**

### そこで見つかった2つの不具合（同日に修正）

**1. 許可要求が利用者の操作から切り離されていた。**
`subscribe()` は `Notification.requestPermission()` の前に公開鍵を
`await` で取りに行っていた。**Safari は許可要求を「利用者の操作と同じ
処理の中」でしか受け付けない。** await が1つでも挟まると操作との
結び付きが切れ、ダイアログが出ないまま失敗する。

公開鍵は画面の初期化で `prime()` して先に取っておき、押された瞬間は
同期的に `requestPermission` へ入るようにした。`requestPermission` より
前に await が現れないことを試験で固定した
（`tests/test_frontend.py::test_the_permission_request_is_not_behind_an_await`）。

**2. iOS の Chrome・Firefox に Safari の手順を出していなかった。**
これらは中身が WebKit なので Safari と同じ制約を受けるが、
**Chrome のタブで「共有ボタンから追加」を探しても確実ではない。**
まず Safari で開いてもらう案内に分けた（`push.iosOtherBrowser`）。

利用者は Chrome で試して「チェックが付かない」と報告した。**仕様どおりの
挙動だったが、案内が足りなかった。**

**押しても何も起きない操作は置かない。** 無効なチェックボックスを残すと、
利用者は押してから初めて反応しないと気づく。説明が下にあっても押した指の
下からは見えない。操作ごと消して手順だけを残した。

もう一点、**iOS の「ホーム画面に追加」は manifest の `start_url` ではなく
その時に開いていた URL を使う版がある。** モニター画面から追加すると、
アイコンがそのモニターを直接開く（トークン入り）。害は無く、むしろ
利用者には都合がよいが、挙動として把握しておくこと。

## 10. 段階

| A | VAPID鍵の生成と保管、購読テーブル、Service Worker、購読API | ✅ 2026-08-20 |
|---|---|
| B | 送信処理（pywebpush）。①だけ。日次ジョブに組み込む | ✅ 2026-08-21 |
| C | ②を足す。往復は除外 | ✅ 2026-08-21 |
| D | manifest.json と iOS の案内 | ✅ 2026-08-21。**実機（iPad）で購読まで確認** |

**Aを配備しても何も送らない。**

**当初「購読を貯めるだけ」と書いたが、これは誤り**（2026-08-20 訂正）。
送れないのに許可を求めるのは、②の案を却下した理由そのもの — 許可は一度
断られると出し直せないので、届かない期間に許可を使うと、Bで送る手段を
失いかねない。

**したがってAでは VAPID 鍵を環境変数に入れない。** `push_enabled` が
False のままなので、購読ボタンは画面に出ず、購読 API も 503 を返す。
コードは載るが眠っている。Bで鍵を入れた瞬間に、送信と購読が同時に立ち上がる。

鍵はAのうちに作ってサーバに置いておく（Bで env に足すだけにする）。

## 11. 実際に送った1通目（2026-08-21）

判定を手で走らせたところ、②が1件送信された。

| SAN→HND 2026-10-08（片道） | 開始日 8/17（5日前）。作成 8/9 → **送信** |
|---|---|
| NRT→SAN 2026-09-01（片道） | 開始日 7/11（42日前）。作成 8/12 → **抑制** |
| 往復2件 | ②の対象外 |

**42日前のものが抑制されたのは、同日に入れた修正が効いた形。** 作成日が
開始日より後なので、そもそも「これから上がります」と言える状態ではない。

## 12. 導線 — 設定タブの中では見つからない（2026-08-29）

段階Dまで終えて配備したが、**購読は126件のモニターに対して5件（4%）**しか
集まらなかった。8日間で送信0通。

**原因は置き場所。** 通知の操作は「⚙️ 設定」タブ（4番目）の中にしかなく、
利用者が最初に見るのは Dashboard。設定まで辿り着く人がほとんどいない。

**値上がり開始日を読んでいるところで誘う。** 「価格トレンド」タブの
`sweetSpotNote`（「◯月◯日から上がりはじめます」）の直下に
「その日が来たら知らせる」を置いた。**その日付を気にしている、いちばん
動機の高い瞬間**で、通知の中身と誘い文句が一致する。

出さない条件を守ること（**送らない通知を誘うのは嘘になる**）:

- **往復には出さない。** ②を送らないため（notify.py の return_date ガード）
- **開始日を過ぎていたら出さない。** 「これから上がります」の知らせなので
- 購読済み・サーバ側で無効・公開鍵が未取得のあいだは出さない

**公開鍵が揃うまでボタンを出さない**のが要。`Push.prime()` の完了前に
出すと、押された瞬間に fetch が挟まって Safari で許可ダイアログが出ない。

受け取れない端末（iOS のタブなど）には、ボタンではなく手順を1行だけ置く。
設定タブまで来ない人にこそ手順が要る。

**効果は購読数で測る。** KPI の push_subscriptions / push_watches。

## 13. 決めきれていないこと

- **通知の文面。** 断定の度合いは「買え と言わない」で固定したが、
  実際に届いたものを利用者がどう受け取るかは分からない
- **1モニター1日1通で足りるか。** 最大 3.5回/週の系列がある
- **複数端末。** 同じモニターを2台で購読したら2通行く。まとめるべきか
- **猶予7日は長いかもしれない。** 上の1通目は開始日から5日後に届いた。
  通知を入れる前に開始日を過ぎたモニターが拾われた形で、間違ってはいないが
  「ここから上がります」としてはやや遅い
- **②を送ったあと出発日が変わることは無い**（モニターは出発日ごと）ので
  再送の考慮は不要
