## 1. 確認事項（プラン提示前に私に質問すること）

以下は仕様が確定していません。**推測で決めず、必ず選択肢と推奨案を添えて私に確認**してください。

1. **技術スタック**: A（Python）と B（Node.js）で言語が異なる。統一するか、収集＋予測=Python / Web=Node の二層にするか
2. **価格データソース**: `fast_flights`（Google Flights スクレイピング）は AWS の固定 IP から叩くと**ブロックされるリスクが高い**。
   - 案1: `fast_flights` 継続 + プロキシ（BrightData 等）
   - 案2: 公式 API（Amadeus Self-Service / Kiwi Tequila 等）に移行
   - 案3: 併用（公式 API を主、スクレイピングを補完）
   コスト・信頼性・実装量のトレードオフを整理して提案すること
3. **買い時アラートの通知手段**: 匿名前提（後述 2.4）なのでプッシュ通知の宛先がない。
   - 案1: 通知なし（ユーザーが URL を再訪して確認する）— MVP はこれで十分か
   - 案2: モニター単位で**任意入力のメールアドレス**を持たせる（パスワードなし＝匿名性は維持）。ただし SES 構成・バウンス処理・配信停止リンクが必要になるので別 Phase に切り出す
   どちらを Phase 4 のスコープに入れるか確認すること
4. **モニター登録の上限値**: 匿名なので登録を人単位で縛れない。日次クエリ数＝**監視中の異なる `(出発空港, 到着空港, 出発日)` の数**に比例するため上限が必須。具体的な数値（IP あたりの登録レート、システム全体の同時監視ルート数上限）を提案し、私に確認すること
5. **原油価格データ**: どのソース・指標を使うか（EIA API の WTI/Brent、Yahoo Finance 等）。またサーチャージへの反映は**実際には数ヶ月遅れる**ため、予測モデルにどう組み込むか
6. **予測の出力形式**: 予測方式そのものは 2.5 で決定済み。確認したいのは UI への出し方。
   - 「今買うべき / 待つべき」の2値に集約するか、予想最安値・最安になる日付レンジまで出すか
   - **不確実性をどう表現するか**（グラフ上の帯、確信度ラベル「データ3日分・参考値」など）。2.5 の要件により予測は必ず区間を持つので、それを UI で潰さないこと
7. **AWS 構成**: PI-27 と同じ Lightsail + PM2 + Nginx（安価・単純）か、サーバーレス（Lambda + EventBridge + DynamoDB/RDS + S3/CloudFront、スケールする）か。想定月額予算も確認したい
8. **通貨・言語**: USD 固定か多通貨か。UI は日英併記（PI-27 に `i18n.js` あり）を踏襲するか

## 2. 機能要件

### 2.1 背景
航空券価格は、航空会社の Revenue Management アルゴリズム、予約状況、出発曜日・到着曜日、祝日、シーズン、原油価格由来のサーチャージなど多数の要因で変動する。旅行者は「最も安く買えるタイミング」を知りたい。

### 2.2 コア機能
- ユーザーが **出発空港・到着空港・出発日** を指定してモニターを登録できる
- **1日1回**、登録された全ルートの現在価格を自動取得する
- モニター開始日からの価格履歴を蓄積し、グラフで可視化する
- 出発日までの価格推移を予測し、**購入タイミングをガイド**する
- 予測の入力は3つ: ①モニター開始日からの日次実測価格 ②航空会社の Revenue Management アルゴリズム（モデル化） ③原油価格トレンド

### 2.3 モニター対象の範囲
- 同一の出発／到着ペアについて、**nonstop と 1-stop の全航空会社**の価格をモニターする
- ユーザーは航空会社をフィルターで絞り込める
- **SAN 特例ルール**: 到着空港が San Diego (SAN) の場合、出発空港→LAX の便も候補に含める。ただし **LAX-SAN 間の便自体は不要**（陸路等で自己接続する前提）
  - この特例は SAN 以外にも将来拡張しうるので、ハードコードせず「近接空港マッピング」として設定で持たせること

### 2.4 マルチユーザー — 匿名マルチテナント（**決定済み・変更不可**）

ログイン認証は実装しない。扱うデータ（空港・日付・航空会社フィルター）に秘匿性がなく、パスワード管理・リセットフロー・個人情報保護のコストに見合わないため。以下の方式で実装すること。

**URL トークン + localStorage インデックスのハイブリッド:**
- モニター登録時に**推測不可能なトークン**（128bit 相当。UUIDv4 / ULID / 22文字 base62 等。**連番 ID は不可**）を発行し、`/w/{token}` を返す。この URL が実質のアカウントになる
- ブラウザの localStorage に、そのブラウザが作成した token の一覧を保持し、再訪時に「あなたのモニター一覧」として表示する
- localStorage を消しても、ブックマークまたは共有された URL があれば復旧できること（**localStorage を正とせず、サーバ側の token を正とする**）
- URL を渡すだけで他人との共有・別デバイスからの閲覧ができること
- トークンは **capability として扱う**。URL を知っている＝閲覧・編集できる、という前提でよい

**収集の重複排除（重要）:**
- モニター（ユーザー視点）と収集対象（システム視点）を**別テーブルに分離**すること
  - `watches` — token, 出発/到着空港, 出発日, 航空会社フィルター, 作成日時, 最終アクセス日時, 有効期限
  - `monitored_routes` — `(出発空港, 到着空港, 出発日)` で一意。日次収集ジョブはこのテーブルだけを見る
- 複数ユーザーが同じルート・同じ出発日を登録しても、**価格取得は1回に集約**される
- これにより API コストは**ユーザー数ではなく異なるルート数**に比例する

**ライフサイクル管理（匿名ゆえに必須）:**
- 出発日を過ぎたモニターは自動的に収集対象外にする
- 一定期間アクセスのないモニターは自動停止・削除する（期間は設定可能に）
- どの `watches` からも参照されなくなった `monitored_routes` は収集を止める
- 放置されたモニターの価格を無期限に取得し続けないこと（課金だけが残るため）

**濫用対策:**
- IP 単位のモニター登録レート制限
- システム全体の「同時監視中の異なるルート数」上限。上限到達時は新規登録を明示的に拒否する（黙って収集を落とさない）

### 2.5 予測方式 — 較正付きドメインモデル（**決定済み・変更不可**）

**マネージドな学習型時系列予測サービスは使わない。** 既存 `simulator.py` + `predict.py` の「ドメイン知識で価格曲線の形を持ち、実測値で較正する」方式を引き継ぎ、改良する。

**Amazon Forecast は検討対象外**（新規顧客への提供が2024年7月29日に終了済み。API 自体が使えない）。SageMaker / Chronos 等の代替も、以下の理由により**初期フェーズでは採用しない**:
- 系列が短く出発日で必ず途切れる（1系列あたり最大60日程度、翌年の同日は別系列）
- 匿名で自由にルート登録できる仕様上、**予測が最も必要な瞬間に履歴がゼロ**（コールドスタートが常態）
- 解きたい問題は「次の値の予測」ではなく「**残り期間の最小値がいつ・いくらか**」であり、汎用の時系列予測 API の出力形式と噛み合わない

ドメインモデルはデータ1点から動き、ゼロ件でもシミュレータ単体で形が出せる。これは学習型では原理的に不可能であり、本アプリの制約に対する妥当な解である。

**必ず修正すべき既存実装の欠陥3点:**

1. **較正の頑健化（最優先）** — 現行は `scale = last_price / sim_at_last` と直近1点の比のみ。スクレイピングの外れ値や一時的なセール価格が1回混じると出発日までの予測全体がズレる。**直近 N 点の比率の中央値、または窓内の最小二乗フィット**に変更すること
2. **「買い時」から過去日を除外** — 現行は `observed`（過去）込みで最小値を探すため、推奨日がすでに過ぎた日付になり得る。「7月3日に買うべきでした」は購入ガイドとして機能しない。**「過去最安値の記録」と「これからの推奨購入日」を明確に分離**すること
3. **不確実性の出力** — 現行の予測は決定論的な1本の線で、実測3日分と40日分が同じ確信度に見える。**予測は必ず区間（信頼帯）を持たせ、観測データ点数に応じて幅が変わる**こと。少ないほど広い

**将来の拡張（Phase 3.5、ML 導入より優先）:**
- 完了した出発日の系列が貯まったら、`_proximity_factor` の「45〜75日前が底」等のハードコード定数を、**自前の実測データから路線・シーズン別に推定した値で置き換える**
- これによりマネージドサービスも学習基盤も不要のまま「形が実測から学習しない」という現行の弱点を解消できる
- 本格的な ML（SageMaker AI + AutoGluon-TimeSeries、または時系列基盤モデル Chronos のゼロショット推論）は、**完了系列が30本程度貯まってから**改めて評価する。その際も常時稼働エンドポイントは持たず日次バッチ推論に留めること

**予測精度の検証:** 過去に出した予測値と、実際にその日に観測された価格を突き合わせられるようログを残すこと（Phase 3.5 以降の判断材料になる）。

## 3. 非機能要件・制約

- **レート制限とマナー**: 既存 `config.py` の `REQUEST_DELAY_RANGE_SECONDS` / `MAX_RETRIES` / 指数バックオフを踏襲する。取得元に負荷をかけない
- **障害耐性**: 日次収集は一部が失敗しても全体をクラッシュさせない（既存 `run_daily.py` の方針）。収集結果は `collection_logs` 相当のテーブルに記録する
- **秘密情報**: API キー等は `.env` / AWS Secrets Manager 経由。**コードにハードコードせず、リポジトリにコミットしない**
- **テスト**: 予測ロジック・DB 層・シミュレータには必ずテストを書く（既存 `tests/` を踏襲）
- **タイムゾーン**: 収集ジョブとユーザー表示のタイムゾーンを明示的に決める（PI-27 は `TZ=America/Los_Angeles`）
- **データ保持**: 予測精度の検証のため、過去の予測値と実際の価格を突き合わせられるようにログを残す
  - ただし **`watches` の削除と価格履歴の保持は分離**すること。モニターが消えても収集済みの価格履歴は資産として残す（同じルートを誰かが再登録したとき即座に過去トレンドを見せられる）
- **匿名トークンの扱い**: トークンは暗号論的乱数から生成する。アクセスログ・エラーログ・外部送信先にトークンを平文で残さない（URL 全体をログに出さない）
- **robots/クローラ**: `/w/{token}` は `noindex` にする。共有 URL が検索エンジンに載らないようにすること

## 4. 進め方（フェーズ分割）

各フェーズ完了時に動作を確認し、私の承認を得てから次へ進んでください。

| Phase | 内容 | 完了条件 |
|---|---|---|
| 0 | 既存2プロジェクトの調査、確認事項のヒアリング、プラン合意 | プラン承認 |
| 1 | プロジェクト雛形・DB スキーマ・設定の外出し | `init-db` が通る |
| 2 | 価格収集層（複数ルート・LCC 明示検索対応・SAN 特例） | 手動実行で実データが入る |
| 3 | シミュレータ＋予測エンジン（原油価格トレンド組み込み、2.5 の欠陥3点を修正） | 外れ値を1点混ぜても予測が崩れない・推奨日が未来日のみ・予測が信頼帯を持つ、をテストで確認 |
| 4 | Web アプリ（登録・グラフ・フィルター・予測表示）＋匿名マルチテナント（トークン発行・共有 URL・localStorage 一覧） | 別ブラウザから共有 URL で同じモニターが開ける |
| 5 | 日次スケジューラ＋ライフサイクル管理（期限切れモニターの停止・収集の重複排除） | 2ユーザーが同一ルートを登録してもクエリが1回に集約されることを確認 |
| 6 | AWS デプロイ | 公開 URL で動作 |

**Phase 6 の AWS デプロイは、実行前に必ず構成・想定コストを提示して私の承認を取ること。** 承認なしに AWS リソースを作成しないでください。
