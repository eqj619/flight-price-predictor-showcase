# 課題一覧

このアプリが抱えている問題を1件ずつ積む。**新しい課題は末尾に追加する**
（番号を振り直さない。過去のやりとりで番号を参照することがあるため）。

## このアプリの目的（深刻度はこれを基準に判断する）

**購入価格を正確に示すことではなく、価格変動のなかで「いま底値の時期か」を
言い当てること。**（2026-08-15 に明確化）

利用者の実際の使い方も、この順序になっている。

1. このアプリ（および Google Flights）で、**どの時期・どのルート・どの航空会社が
   良さそうか**の当たりを付ける
2. 実際の予約は**航空会社のサイトで調べ直す**

したがって:

- **表示価格が航空会社の直販価格と一致しないことは、致命傷ではない。**
  利用者は最終的に別の場所で買う
- **一方、いつが安いかを外すと、このアプリは存在価値を失う**

**深刻度は「タイミングの判断をどれだけ損なうか」で測る。金額の正確さは二次。**

## 1. 記録している価格が「単一の量の時系列」になっていない

**状態: 未着手**（2026-08-15 記録）

### 症状

利用者からの指摘（報告）:

- Google Flights の検索結果には**旅行会社（OTA）の価格が混ざっており、フィルタで
  除外できない**。この点は利用者から不満が多い
- そのため**表示価格が実際に買える価格を反映しないことが増えている**
- 旅行会社経由で予約すると、**遅延・欠航が起きたときに対応で問題が生じる**ケースが
  少なくない
- Google Flights で見たあと航空会社のサイトで予約しようとすると**もっと高い**ことがある

結果として、利用者は「Google Flights でどの時期・どのルート・どの航空会社が
良さそうかの当たりを付け、実際の予約は航空会社のサイトで調べ直す」という
使い方をしている。

### 影響

**目的（いつが底か）に照らすと、深刻度は中。** 金額の正確さは二次だから。

| 観点 | 影響 | 目的への効き |
|---|---|---|
| 表示金額が直販と違う | 航空会社では買えない額の可能性 | **小。** 利用者はどのみち別の場所で買う |
| 手荷物代を含まない | LCC が有利に見える | **小。** 課題 8 |
| **値動きに売り手の交代が混ざる** | 運賃が動かなくても値が動く | **中。タイミングの判断を鈍らせる** |
| 学習の目的変数 | 「運賃」ではなく「買える最安値」 | **将来のモデル次第** |

**残る問題は3行目だけ。** 「いつ底か」を当てるには値動きの形が要るが、その形に
売り手の交代が混ざっている。**どれだけ混ざっているかは測れない**（④⑤のとおり
売り手を知る手段がない）。

**幸い、目的が金額ではなくタイミングなので、記録している量の定義は目的と
むしろ整合している。** 利用者が実際に直面するのは「その日その便を買える最安値」
であって、特定の売り手の運賃ではない。**その系列の底を当てることは、利用者に
とって意味のある問いになっている。**

将来モデルを作るときは、目的変数を「その便の運賃」ではなく
**「その日その便を買える最安値」**として明示的に扱うこと。運賃の値付け構造を
学習しようとすると、売り手の交代が混入して失敗する。

### 確認したこと

**① 検索結果の生データに、予約先の情報は一切含まれていない**（2026-08-15 実測）

`fast_flights` が解析している Google Flights の応答を直接調べた。1便あたりの
構造は次のとおりで、価格は整数が1つあるだけ。

```
k[0] = ["NH", ["ANA"], [...], "NRT", [2026,10,29], ...]   便の情報
k[1] = [[None, 2152], "CjRIdEJ4bWZhRW9zRnNBRzRMZEFC"]      価格 + 何かのトークン
k[8] = "["CAISA1VTRBoECJeRDSJ1CloKWA"                       同上
```

`Expedia` `Trip.com` `Kiwi` `eDreams` `Gotogate` `Booking` `Priceline` `Orbitz`
`agency` `provider` などの語で全体を検索したが**1件も出てこない**。

**したがって、いま取っているデータからは航空会社直販か OTA かを判定できない。**
これはライブラリの制約ではなく、検索結果の応答自体に無い。

**② 価格の内訳も持っていない**（2026-08-14 実測、課題とは別に確認済み）

税・手数料は含まれる（Google の公式ヘルプ「Our prices include standard taxes
and fees」）が、内訳は返らない。受託手荷物は含まれない。

**③ 同一路線・同一日で価格が14倍開くことがある**（2026-08-12 実測）

```
SAN→HND 2026-10-29
  $594    SAN-DFW-HND   American
  $938    SAN-SFO-HND   Alaska, JAL
  $8,423  SAN-SFO-HND   Alaska, United   ← 同じ経路で 9倍
```

売り手や運賃クラスの違いを示唆するが、**データ上は区別できないため断定はできない。**

**④ 1便につき価格は1つしか返らない**（2026-08-15 実測）

同じ便（航空会社・経由・出発時刻・到着時刻がすべて一致）が複数の価格で返って
こないかを調べた。**重複はゼロ。** 売り手ごとの内訳も、複数の売値も返らない。

```
NRT→LAX 2026-10-29   6件  同一便の重複なし  価格 $612〜$2,284
SAN→HND 2026-12-08   4件  同一便の重複なし  価格 $557〜$8,001
```

**⑤ トークンにも予約先は入っていない**（2026-08-15 実測）

`k[1][1]` と `k[8]` を base64 として復号した。

```
k[8]: ...USD..."u.Z.X..NRT..2026-10-29T17:00:00+09:00..LAX"
      .2026-10-29T10:50:00-07:00*.NH2.6
```

中身は**便の情報（空港・時刻・便名・通貨）だけ**。`k[1][1]` は全便で同一で、
検索そのものの識別子と見られる。**売り手を知る手がかりは検索結果のどこにもない。**

### 記録している量は何か

上記から、`snapshots.price_usd` が表しているのは次の量である。

> **その日その便を、いちばん安く売っていた誰かの価格**

これは「その便の運賃」ではない。**変動する売り手集合の最小値**である。
結果として:

- **系列が単一の量の時系列になっていない。** 売り手が入れ替われば、運賃が
  1円も動いていなくても値が動く
- **常に最小値なので、特定の売り手から見れば下方に偏っている**
- **分解できない。** 値動きのうち何%が値付けの変更で、何%が売り手の交代かを
  測る手段が、この取得元には無い

**これは便の入れ替わり（2026-08-13 に対処済み）と同じ構造だが、そちらと違って
検知も除去もできない。** 便の交代は `stops / via / airline` が変わるので見えたが、
売り手の交代は何も変わらない。

**取得元を替えない限り避けられない。**

### 対応の選択肢

| 案 | 内容 | 代償 |
|---|---|---|
| **A. 何もせず、画面で明示する** | 「価格は各種販売経路の最安であり、航空会社の直販価格とは限らない」と表示 | 実装は軽い。**問題は解決しないが、誤解は解ける** |
| B. 予約オプションを取得する | 便ごとに別リクエストを投げ、売り手の一覧と価格の幅を得る | 日次リクエストが数倍。**トークンに予約先が入っていないことは確認済み**なので、別の入口を探す必要がある |
| C. 航空会社直販のみに絞る | B で判別したうえで直販だけを残す | B の代償に加え、**最安が消えて価格帯が上がる**。利用者の期待とずれる可能性 |
| D. 取得元を公式 API に替える | Amadeus など。売り手が明確 | `PriceProvider` 抽象があるので差し替え自体は可能。ただし有償・レート制限あり |

**まず A を実施し、B の実現可能性を別途調べる**のが順当と考える。
A は誠実さの問題で、B/C/D は精度の問題。順序を逆にすると、判定が信用できない
まま利用者に見せ続けることになる。

**ただし B〜D はいずれも「取得元を変える」話であり、この取得元を使い続ける限り
この問題は残る。** 学習データの目的変数の定義（上記）を正しく記録しておくことが、
いま確実にできる唯一の対処。

### 関連

- 価格の内訳（税・手数料）については README「所要時間による除外」の周辺に記載
- 取得元の差し替えは `app/collect/provider.py` の `PriceProvider` 抽象で可能

> **2026-08-15: 待たずに実測できることが分かった。** 取得元が応答に過去約61日分の
> 価格履歴を載せており、我々はそれを毎日受け取りながら捨てていた。稼働中223ルートに
> 遡って取り込み、**212系列 / 13,004点**を得た。完了系列（最初は 2026-08-23）を
> 待つ必要はなくなった。
>
> **結果は「モデルは半分合っていた」。** 詳細は [price-curve-2026-08-15.md](price-curve-2026-08-15.md)。

> 便ごとの予測に当てている。初の実測突き合わせで予測が中央値 +15.3% 高く、
> 直前の急騰が実測に出ていなかった

> **パラメータの再推定より前に、推定元と適用先を揃えるかどうかを決める必要がある。**

### 症状

このアプリの目的は「いつ買うか」を示すことだが、**その判断は全面的に価格曲線に
依存しており、曲線は実測から推定した値ではない。**

```python
verdict = _decide(current_best, predicted_min)
             ↑ 実測（今の価格）  ↑ モデル（未検証）
```

実測が使われているのは「今いくらか」だけ。上がるか下がるかはすべて曲線が決める。
**実測の値動きそのもの（方向）はどこでも計算していない**（コード全体を検索して確認）。

### 影響

**製品の中核が最も根拠の薄い部分に乗っている。**

| 利用者が知りたいこと | 状態 |
|---|---|
| 今いくらか | 実測。確か |
| いくらまで下がりそうか | モデル。較正で水準は改善する |
| **いつ下がりはじめるか** | **モデルのみ。未検証** |
| **いつ上がりはじめるか** | **モデルのみ。未検証** |

### 確認したこと

**① 底値帯 45〜75日前は判断で置いた初期値**（`curve.py` 自身が Phase 3.5 の
推定対象だと書いている）

**② 2026-08-11 の断面では支持されなかった**

実測の最安が出た日は 28 / 79 / 79 / 79 / 79 / 112 / 118 / 118 日前で、
**45〜75 日前に入るものは 0/8**。モデルの順位一致は 5/8。ただし出発日をまたぐ
断面なので季節性と交絡する。反証ではないが、支持する証拠でもない。

**③ Google Flights の実測履歴と形が違う**（2026-08-15、利用者提供の画面より）

`SAN → 東京都 / 2026-12-08 出発`（往復）について、Google が表示した過去55日の
価格推移と、同じ期間・同じ出発日でうちのモデルが言うことを比べた。

| | うちのモデル | Google の実測 |
|---|---|---|
| 期間 | 出発 170日前 → 115日前 | 同じ |
| 変動幅 | **6.2%** | **34.8%** |
| 形 | なめらかに単調減少 | **途中で +13% 上昇してから下落** |

```
Google の実測（図から目視）
  $1,375 → $1,550 → $1,500 → $1,290 → $1,150

うちのモデル（相対値）
  1.000 → 0.989 → 0.973 → 0.957 → 0.942
```

**モデルはこの区間に上昇を作れない。** 出発75日前より手前は「底値帯より遠い側」
として単調に下げるだけの式で、途中の反転を表現する仕組みがそもそも無い。

*留保:* Google の線は往復（うちは片道）で、かつ「この検索結果」の値なので
**便の入れ替わりが混ざっている可能性がある**（うちのグラフで直したのと同じ問題）。
値は画面からの目視。したがって 34.8% のすべてが価格変動とは限らない。
**ただし「途中で上がる」という形の違いは、混入では説明できない。**

**④ 取得元は「履歴からの学習」で、うちは「判断で置いた式」**（2026-08-15 確認）

Google は方式を公表している。

> based on an analysis of **past prices of similar trips**
> based on an analysis of **price trends of past flights**, and there is always
> a chance that future prices will not behave as we expect
> — [Google Travel Help](https://support.google.com/travel/answer/7664728)

集計の範囲も公表されている。**複数年ぶんの Google Flights データ**、**往復**の
6〜9日間・13〜16日間の旅程、米国の主要市場発。

| | Google | このアプリ |
|---|---|---|
| 形の決め方 | **過去の価格推移から学習** | **判断で置いた式**（45〜75日前が底） |
| 単位 | 似た旅程ごと | 全ルート共通の1本 |
| データ量 | 複数年 × 全世界 | 7日 × 215ルート（2026-08-15 時点） |
| 出せること | 「安い/標準/高い」「値上がりしそう」 | 3値判定・信頼帯・basis の3段階 |

**方式が違う。** うちは形を先に決めて水準だけ実測で合わせるが、Google は形自体を
履歴から出している。③ で形が食い違ったのは、この違いの帰結と考えるのが自然。

なお Google の集計では「似た旅程の最安は**出発2か月前**あたりが多い」とされており、
これは**うちの 45〜75日前と重なる**。**中心の位置は大きく外していない可能性がある。**
問題は、うちがそれを固定値として全ルート・全出発日に当てていることのほう。

**⑤ 較正では直らない**

価格は掛け算で分離されており、較正はスケール項。水準の誤りは実測が貯まるほど
直るが、**タイミングの誤りは永久に残る。**

**⑥ 決着には系列内観測が要る。完了系列は 2026-08-15 時点で 0 本**
（最初の完了は 2026-08-23）

### 対応の選択肢

| 案 | 内容 |
|---|---|
| A. 完了系列から曲線を推定し直す | 8/23 から材料が貯まる。**曲線の形を先に決めず、日数ごとの正規化価格の中央値を直接持つ**ほうが素直 |
| B. 実測の値動きを併せて出す | 「3日間変化なし」「昨日4%下落」は測定だけで言える。転換点は出せないが、モデルに頼らない情報が増える |
| C. 文言で限界を示す（実施済み） | 「検証中」と明示。2026-08-12 に対応 |

**③④ を踏まえると、いまの曲線は「未検証」ではなく「形が違う疑いが濃い」。**
A の優先度を上げるべき。**しかも A の方向（履歴から形を出す）は、取得元が
実際に採っている方式と同じ。** 曲線の形を先に決める現在の作りは、
データが貯まるほど不利になる。

ただしデータ量では勝負にならない（複数年 × 全世界 対 7日 × 215ルート）。
**同じ土俵で精度を競うのではなく、根拠を示せることや近接空港の横断比較で
差を出す**という整理が要る（課題 11）。

## 3. 繁忙期を価格曲線が表現できない

**状態: 調査中**（2026-08-15 記録）

### 症状

感謝祭・クリスマス・年末年始は予約が早く入り、価格の底も早く来ると予想されるが、
**モデルは出発日によらず常に「45〜75日前が底」と答える。**

### 確認したこと（2026-08-12 実測）

**状態: 未着手**（2026-08-15 記録）

収集は毎日 03:00（太平洋時間）の1回のみ。航空券の価格は1日のうちに複数回

### 確認したこと（2026-08-13 実測）

同一便を翌日と突き合わせた1,002組:

```
日次変化   平均 1.61%   変化なし 49%（490/1002）
動いた日だけ 平均 3.1%   最大 65.6%
```

（何時に、何回）が分からない。

### 影響

- 「上がりはじめた」の検出が最短でも1日遅れる
- 学習データとして日内の変動が失われる
- 直前期（価格が速く動く時期）ほど取りこぼしが大きい

### 対応の選択肢

頻度を上げると日次リクエストが比例して増える。現在 645回（215ルート × 3検索）で
所要 42分。**1日2回にすれば所要も負荷も倍。** 出発が近い系列だけ頻度を上げる、
といった絞り方が現実的と考える。

**状態: 未着手**（2026-08-15 記録）

### 症状

利用者提供の Google Flights の画面（2026-08-15）に、**このアプリが作ろうと

### 取得元の方式（2026-08-15 確認）

Google は算出方法を公表している。

- 「安い / 標準 / 高い」は**過去の似た旅程の価格から**判定
- 「値下がりしなさそう」「値上がりしそう」は**過去の価格推移の分析**による

  prices will not behave as we expect"）

### 影響

**このアプリの立ち位置を問い直す必要がある。** 取得元が同じ情報をより広い
カバレッジ（往復・全世界・全クラス）で、しかも**複数年のデータに基づいて**
無料提供している。

一方で、このアプリにあって Google Flights に無いものもある。

- **近接空港をまたいだ比較**（HND/NRT × SAN/LAX を1画面で追う）
- **複数の出発日を並べて監視する**（出発日ラダー）
- **蓄積した実測を自分のデータとして持てる**（学習データ、エクスポート）

- Google は**方式は公表しているが、個々の判定の根拠は出さない**（何件の履歴に

  その根拠自体がまだ検証中
- **データ量では勝負にならない。** 同じ土俵で精度を競う設計にしない
- 汎用モデルの学習データを貯めるという目的は、Google の表示では代替できない
- **利用者にとっての価値**と**データ資産としての価値**を分けて考えるべき

## 13. 実測が揃ったら、曲線を機械学習に置き換える

**状態: 待ち（データ待ち）**（2026-08-24 記録）

### やりたいこと

いまの予測は**手で決めた形の曲線1本**でできている。路線も航空会社も季節も
曜日も、固定の係数を掛けるだけで、実測から学んだものではない。

実測が貯まったら、**路線・航空会社・季節・曜日・イベント（連休、繁忙期）**
を特徴量として学習させ、予測に反映させたい。

### いまの作りとの差

| | いま | 学習に置き換えたら |
|---|---|---|
| 形 | 全ルート共通の1本の曲線 | 路線・便ごとに違ってよい |
| 航空会社 | 固定の係数表（`airline_factors`）。**較正で丸ごと吸収される** | 実測から学ぶ |
| 季節 | 月ごとの固定係数（`seasonality`）。**推定していない** | 実測から学ぶ |
| 曜日 | 固定係数（`day_of_week`）。**推定していない** | 実測から学ぶ |
| イベント | **無い** | 連休・繁忙期を明示的に入れる |

`curve.py` の季節・曜日の係数は既存アプリから引き継いだ初期値で、
**一度も実測から推定していない。** ここは学習で置き換える価値が大きい。

### 着手前に決めておくこと — ここを飛ばすと必ず失敗する

**1. 目的変数を何にするか。**

課題1のとおり、我々が記録しているのは「その便の運賃」ではなく
**「その日その便を買える最安値」**。学習の正解をここに揃えないと、
値付けの構造を学ぼうとして売り手の交代を学ぶことになる。

**2. 便ごとか、ルート最安か。どちらの量を予測するのか。**

**課題9でこれを取り違えていたことが分かった**（2026-08-24）。曲線は
`price_history`（便を特定しない最安値）から推定したのに、便ごとの予測に
当てていた。結果、出発直前で予測が +18.7% 高く、信頼帯は 49% しか
当たらなかった。

    ルート最安  安い便が売り切れれば上がる（日次 5.27%）
    便ごと      その便の値段だけ（日次 1.61%）

**学習でも同じ罠がある。** どちらを予測するのかを先に決め、学習データも
評価も適用先もその1つに揃えること。

**3. 「正解」が確定するのは出発日を過ぎてから。**

`export_snapshots(completed_only=True)` が既にある。途中で切れた系列は
「残り期間の最小値がいくらだったか」が確定しないので学習に使えない。

   （特徴量に出発月は入っているが、学習データは 8〜10月だけ）

## 17. 底値の判定に機械学習を使えるか

**状態: 影で計測中（2027-01 中旬に判断）**（2026-10-23 記録）

### 判定の当たり外れ（10/12〜10/23、答え合わせ 36件）

| 判定 | 件数 | 当たり |
|---|---|---|
| 今買う | 13 | 77% |
| 待つ | 17 | 47% |
| 様子見 | 6 | 17% |

36件はすべて出発の2〜9日前の判定。予測した底値の日に買うと底値より平均 +22.6%、
判定の日にすぐ買うと +22.3% で、**今の判定はすぐ買う以上の得を出していない。**

### 機械学習の当て直し（`scripts/backtest_buy_policy.py`）

問いは「今日買わずに待つと、14日以内に5%以上下がるか」（毎日が1つの例）。
自前の実測だけ、出発日で学習と確かめを分けた（10/5 より前の出発 52便 → 以降 44便）。

| 見始めた日 | すぐ買う | 決まった日 | 下がる確率の表 | 勾配ブースティング |
|---|---|---|---|---|
| 45日前 | +35.4% | +28.1%（31日前） | +76.5% | **+22.5%** |
| 30日前 | +22.7% | **+13.3%**（23日前） | +17.4% | +14.4% |
| 21日前 | +9.4% | +9.4%（21日前） | +8.2% | **+6.6%** |

- 「下がるか」の当たり具合 AUC 0.69（表は 0.61）
- 勾配ブースティングは、すぐ買うより 3〜13 ポイント小さい。**学習と確かめを入れ替えても同じ向き**
- **ただし差の95%区間は多くの条件で 0 をまたぐ。** 決まった日に買う場合とは互角
- 下がる確率の表は区分ごとの件数が少なく不安定で、採らない
- 本当の意味の例の数は「便の数」（約100）で、閑散期1シーズンしかない

### 対応（2026-10-23）

**本番の助言には使わず、影で動かす**（利用者の判断）。外部サービスは使わず、
今のサーバに scikit-learn を足した（`app/ml/drop_model.py`）。

- 毎朝の判定の段階で「14日以内に5%以上下がる確率」を `verdict_log.ml_drop_prob` に残す
- 学習はモデルが無いか28日以上前なら、出発日を迎えた便で作り直す（出発済みが30便未満なら見送り）
- 失敗しても判定の記録は止めない。`ML_SHADOW_ENABLED=false` で止められる

### 判断の目安（2027-01 中旬）

1. 年末年始の便を含めて `scripts/backtest_buy_policy.py` を流し直し、すぐ買う・決まった日との
   差の95%区間が 0 をまたがなくなっているか
2. 影で残した確率を使った買い方が、同じ期間の今の判定（今買う／待つ）より底値に近いか
3. 両方を満たしたら、「待つ」の判定に機械学習の確率を使う
